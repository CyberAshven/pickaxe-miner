# Contract profile

Each network's contract is a `PhotonDeployment` in `src/protocol.rs`: category ID, P2SH32 locking bytecode, Electrum script hash, redeem script, covenant address and proof rule. `verify()` rejects a deployment whose redeem script, lock and script hash disagree. Mainnet and Chipnet run the author's v3.2 contract (`template.v3.2.json` in 2qx/vox: a 273-byte redeem script, script hash `0cea1bfb…5261`, whose proof rule requires a positive hash and target) and differ only by category. `reference/photon_v32_chipnet_confirmed_parent.hex` is a confirmed Chipnet claim on it, which the miner rebuilds byte for byte.

To adopt an independently reviewed deployment, replace those fields together, rebuild the miner, and validate the complete path: live baton discovery, GPU search, winner reconstruction, node acceptance and journal recovery. Use an authorized test deployment first. Static fixtures and compilation alone do not establish compatibility; production promotion requires end-to-end evidence.

GPU kernels are compiled per layout shift over the original 615-byte v0 mining transaction (`PhotonLayout::GPU_SHIFTS`): shifts 0..=3 for the v0 reference vectors and 14..=16 for v3.2, whose redeem script is 14 bytes longer. v3.2 can therefore be mined at baton ages up to 32767; at 32768 and older its transaction would need an eleventh SHA-256 block. Other layouts are rejected before a job reaches the GPU. A contract of another length needs its shifts added to `GPU_SHIFTS`, the Rust, CUDA and HIP kernel lists and rebuilt GPU code, plus end-to-end validation. The experimental wgpu backend reads the layout shift from its input block at run time, so one compiled shader serves every GPU layout above; it takes the same shifts as `GPU_SHIFTS`.

`protocol/photon.json` and `reference/` keep the retired v0 deployment for the VM proofs of its layout and self-funded settlement.

Resolve any pending submission with its matching miner before switching profiles. Journals are bound to the category and script hash, and a mismatched journal is preserved and rejected. Older journals remain bound to the original deployment. Keep the previous binary and journal until any uncertain broadcast outcome has been resolved.
